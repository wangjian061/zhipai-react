# V1.4.6｜通知业务规则

更新：2026-11-03。适用：专项采集相关通知及App版本更新，面向产品、iOS、Android、鸿蒙、服务端与测试。

已确认的通知／强更结构参考见本机[通知结构图](../design-previews/notification-services-20261103/01-notifications.svg)。该预览目录未纳入Git，是结构参考，不是实际截图或用户视觉验收结果；规则正文以本文件为准。

## 1. 通知要解决什么问题

让用户及时知道自己的采集是否需要处理、是否已有结果，以及项目安排是否发生变化，并能直接进入对应业务继续办理。

采用两个渠道：

- **APP内通知中心**：查看消息内容和历史记录，进入关联项目或任务。
- **手机系统推送**：用户没有打开APP时，提醒重要事项。系统推送不是新的业务状态，滑掉推送也不会删除站内消息。

## 2. 三类通知分别由谁触发

| 类型 | 内容范围 | 产生方式 | 关联去向 |
| --- | --- | --- | --- |
| 采集通知 | 本人制作失败、审核未通过、采集完成、上网完成、上网失败 | 根据后台确认的业务结果生成 | 原采集任务的最新详情或完成状态 |
| 项目通知 | 采集开放、截止提醒、采集要求调整等项目安排 | 后台人员选择项目和接收人群，填写标题、正文后发布 | 对应项目详情 |
| 系统通知 | 服务维护、版本更新、平台公告 | 后台人工发布，按受影响的平台或人群发送；版本更新结合正式发布配置 | 普通公告查看对应内容；版本更新进入当前适用的升级流程 |

本轮项目通知采用人工发布，不增加按项目开放、截止时间自动发送的规则。「全部」仅为APP内筛选项，不是第四种通知类型。

## 3. 采集通知

### 3.1 哪些结果生成消息

| 通知 | 对应结果 | 用户需要了解什么 |
| --- | --- | --- |
| 制作失败 | 本次照片制作明确失败 | 查看当前任务及处理方式 |
| 审核未通过 | 本次审核明确未通过 | 查看实际审核意见，按任务允许的操作处理 |
| 采集完成 | 照片审核通过，可以查看、保存结果 | 本次采集已完成；不代表已提交学信网 |
| 上网完成 | 后台确认照片已成功提交学信网 | 需要上网的项目已完成该阶段 |
| 上网失败 | 后台确认提交学信网失败 | 查看原因及处理方式，不自动要求重拍或重提 |

五类结果均生成站内通知，手机提醒按3.2及第7节已确认的节奏处理。制作中、待提交审核、审核中继续在办理页面和采集记录中展示，不单独生成通知。后台25与26内部阶段切换不能借此增加一条审核中消息。

### 3.2 需要上网的项目如何推送

| 阶段结果 | APP内通知 | 手机系统推送 |
| --- | --- | --- |
| 采集完成 | 保留 | 不推送 |
| 上网完成 | 保留 | 推送 |
| 上网失败 | 保留 | 推送 |

用户可以在站内查看完整过程，手机重点提醒最终上网结果。制作失败、审核未通过及无需上网项目的采集完成已确认为重要消息，按前台／后台规则提醒；配套规则见第7节，不再列为待确认。

### 3.3 APP前台如何提醒（已确认）

| 用户当前场景 | 提醒方式 |
| --- | --- |
| 正在查看这条采集通知对应的任务 | 页面直接更新业务结果，不重复叠加弹窗或系统横幅；消息仍保留在通知中心 |
| 正在其他普通页面 | 重要消息显示一次可点击的轻提醒，进入对应内容；普通站内消息安静进入通知中心 |
| 正在拍摄、付款或提交 | 不插入提醒、不抢焦点、不打断操作；消息仍保留在通知中心 |
| APP在后台或未打开 | 按已确定的重要消息及人工发布规则发送手机系统推送 |

轻提醒出现或消失不算已读，仍需成功打开对应内容。页面自动更新当前任务结果也不等于用户点击查看了新通知。前台提醒遵循上述避让及已读规则，外观沿用DESIGN和消息反馈规范；正式提醒覆盖层与真实推送仍待补齐，工作区样例不作为已接入证明。

## 4. 人工发布通知

### 4.1 项目通知

发布人员明确：所属项目、接收人群、标题、正文，以及是否同时发送手机提醒。

- 站内通知始终保留，只有选定的用户能收到。
- 后台提供「同时发送手机提醒」选项，**默认关闭**。
- 普通说明只在站内展示；发布人员认为需要提醒手机的重要事项，再开启该选项。
- 不勾选不影响通知发布；勾选也不改变项目状态、认证结果或付款事实。

例如，「补充一份采集说明」可仅发站内；「明天截止采集」可同时提醒手机。这是发布方式的示例，不是自动定时规则。

### 4.2 系统通知

服务维护、重要版本说明及平台公告由后台人工发布，按受影响的平台或人群发送，不默认向所有用户广播。人工系统公告与项目通知共用「同时发送手机提醒」，默认关闭，由发布人员选择。后台具体可选人群、发布权限及接口仍需技术方案核对，不假定本仓库已有管理界面。

### 4.3 版本更新与强制更新（策略已确认）

**每次正式发布新的App版本，该平台、该渠道的所有旧版用户都必须更新后才能继续使用App。** 用户已明确选择这一规则，不采用“只有低于某个最低可用版本才强更、其他旧版可跳过”的产品策略。

- 版本更新属于系统通知中的一种业务，不增加第四种通知分类。
- iOS、Android、鸿蒙分别依据本端、本渠道最新可用的正式版本判断；不能拿另一端的版本号或共同需求迭代号强制本端更新。
- 本方案以用户实际能取得新版为启用条件。仅开发完成、提审、审核通过但尚未发布，均不提前让该渠道旧版用户进入无更新可用的拦截状态。
- 原型Git推送、原型日期版本变化、后台服务单独部署、测试包或尚未正式交付的构建，不自动触发App强更。版本编号仍沿用[既有版本规则](../release-versioning.md)。
- 更新消息负责告知，App内版本检查负责限制继续使用。未收到推送、关闭系统通知、划掉推送或已读消息，都不能代替升级或解除升级要求。
- “去更新”只是进入升级渠道，不等于更新完成；重新检查实际安装版本，符合当前正式发布要求后才能继续。用户可以通过系统离开App，不提供继续使用旧版业务的跳过入口。
- 已更新用户无需再次升级；安装版本高于当前渠道已公布目标的测试或内部包不能被误判为旧版并要求降级。

### 4.4 升级流程与通知衔接（结构及恢复规则已确认）

安全可恢复节点、失败后保留任务并重试、返回核对真实安装版本，以及无取消／跳过的强更结构已确认。版本接口、有效策略缓存、设备兼容及正式发布后的自动消息机制仍需明确，不与已确认的交互规则混写。

| 阶段或情况 | 产品方案 |
| --- | --- |
| 后台准备版本 | 明确平台、分发渠道、正式版本及构建标识、更新说明、更新入口、可获取状态和生效时间。与实际商店／分发记录对应，不预填三端统一版本号 |
| 发布生效 | 先确认对应渠道用户实际可更新，再启用本次强更规则；面向受影响的旧版用户。正式发布是否自动生成更新消息、如何与人工发布及手机提醒衔接，仍需明确机制 |
| 用户进入App | 启动及从后台返回时检查当前适用版本；发现旧版进入升级状态，更新完成前不启动新的业务操作 |
| 用户正在拍摄、付款或提交 | 延续已确认的不打断原则，先妥善保存当前照片／输入及已发起交易，回到可恢复的安全节点再要求升级；不能为显示更新而丢弃任务或重复收费 |
| 用户点击更新并返回 | 重新核对实际安装版本；仍为旧版则仍需更新，不能仅凭去过商店就放行；已更新则退出升级状态，按权限恢复原业务 |
| 更新入口无法打开或更新失败 | 说明未完成更新并提供重试；保留任务和付款事实。不能提示更新成功，也不能自动跳过强更 |
| 版本检查失败或策略异常 | 查询失败不等于发现新版本，不凭空拦截；已有有效强更策略、离线缓存及重试的衔接需开发与产品共同明确 |
| 新版本无法在某设备安装 | 需明确设备兼容与后续支持方式，不能反复要求一次不可完成的升级；该设备的实际支持策略尚未确定 |

已确认升级结构采用标题「发现新版本」、说明「请更新至最新版本后继续使用知拍。」、更新内容和主操作「去更新」，提示从更新渠道返回后重新检查版本；不提供「稍后再说」或「跳过」。正式业务强更尚未接入，本轮只在工作区内存会话演示发现新版、入口失败、仍旧版和模拟完成，不调用商店或执行安装，也不假定后台已有版本管理、SDK或强更接口。

## 5. 历史、已读与点击规则

### 5.1 历史消息独立保留

同一任务先审核未通过、重拍后采集完成，保留两次通知，不能用完成消息覆盖旧失败消息。旧消息保留当时的内容和时间，不随任务后续更新而改写。

点击旧消息仍进入**任务最新状态**。已经完成的任务不再依据旧通知提供失效的重拍、付款或提交操作。通知历史和当前办理状态各自承担职责。

### 5.2 成功查看后才算已读

- 用户从APP内消息或手机推送进入，并成功打开对应任务后，标为已读。
- 仅收到推送、滑掉系统通知或打开失败，不算已读。
- 已读通知继续保留，可以再次查看。
- 项目与普通系统公告成功打开独立完整正文后才标已读；正文包含类型、标题、来源和发布时间，有关联项目时可继续查看项目。正文读取失败、登录取消或目标打开失败不算成功查看。

不增加未经确认的一键已读、清空或删除功能。

### 5.3 已确认页面结构

通知中心保留现有头部、全部／系统／项目／采集筛选与消息白卡，增加独立历史和未读标记。采集通知直接进入原任务当前状态；项目与普通系统通知先打开公告全文，项目公告再提供「查看项目」。返回保留筛选和列表位置。历史消息保留当时内容，不能把旧失败动作重新加到已经完成的任务；目标失效或打开失败不跳转其他任务，也不标已读。以上结构已确认，正式业务UI仍待补齐。

## 6. 开发需要提供什么

### 本轮已确认的产品要求

1. 通知以独立消息记录保存，不能只用采集记录当前状态临时拼成消息列表。
2. 每条消息需要明确类别、标题、正文、发生或发布时间、接收对象、关联项目／任务及查看目标；已读结果需要保存。这里是业务含义，不是约定的接口字段名。
3. 人工发布消息与业务结果消息采用各自来源，按统一通知分类展示；项目发布应具备已确认的可选推送行为。
4. 站内点击和手机推送点击应进入同一业务目标，并查询当前状态、校验当前账号权限。登录、目标失效及打开失败不能标为成功查看。
5. 手机提醒与站内记录分别记录处理结果，不能把已生成通知、已发出推送、手机已收到及用户已读写成同一结果。
6. 版本更新消息与实际版本策略分开管理。强更判断不依赖用户是否读过消息；每端按已发布、可取得的当前渠道版本判断，检查和升级恢复不能改变原有任务、照片或交易事实。后台版本配置及查询协议尚未接入。

### 当前原型差距

当前[通知组件](../../src/components/CollectionNotifications.jsx)已有三类筛选、列表和来源返回；[配置](../../src/domain/collection-config.js)提供固定系统／项目样例；[业务逻辑](../../src/domain/collection.js)按本人采集记录的最新状态生成采集消息。

正常业务目前没有独立历史消息、持久化已读、真实通知发布后台、手机推送或App版本检查／强更接入。这些是后续开发需求，不能写成已完成。[工作区](prototype-workbench.md)现已提供虚构通知历史、未读、公告和升级结果的内存演示，复用通知／任务组件但不写当前业务数据；它不代替正式通知改造。真实上网枚举和结果服务还需与服务端核对，不能直接把原型前端`uploaded`、`upload_failed`当作生产协议。

继续沿用[DESIGN](../../DESIGN.md)、[反馈规范](../design/message-feedback-guidelines.md)及[专项采集规则](../collection-zone.md)。本轮通知／强更结构已确认，无须重复确认同一结构；之后出现实质结构变化时再更新样图。工作区本地实施、正式业务UI、真实接口及用户验收分别记录，不能相互替代。

## 7. 已确认配套规则与剩余交接

下表配套规则已于2026-11-03整体确认，不再作为待定草案；规则确认不表示正式业务或真实推送已完成。

### 配套规则（已确认）

| 情况 | 处理方案 |
| --- | --- |
| 制作失败、审核未通过、无需上网项目的采集完成 | 确定为重要消息，按已确认的前台／后台规则提醒；需要上网项目的完成节奏保持3.2 |
| 后台人工发布系统通知 | 与项目通知共用「同时发送手机提醒」，默认关闭，由发布人员选择；受众仍按受影响平台或人群确定 |
| 同一次业务结果被重复回调、查询或刷新 | 只生成同一条站内通知，不反复发送相同手机提醒 |
| 用户重试后，产生新一次失败或完成结果 | 作为新的结果保留通知；不能因为同一任务曾经通知过就遗漏新结果 |
| 同一任务的旧状态已被新结果取代，提醒尚未发出 | 不再发送已经过时的提醒，站内历史消息保留；已发送的旧消息点击仍打开最新状态 |
| 登录、重装或重新获取历史列表 | 同步历史和已读状态，不集中补推以前的消息 |
| 手机提醒展示什么 | 仅简要标题与查看引导；姓名、证件号、照片和详细失败原因留在登录后的业务内容里查看 |
| 手机推送发送失败后重试 | 仍处理原条消息的推送，不新建一条相同通知，不因重试改变用户已读事实 |

### 仍待明确或接入

1. 通知、已读、目标权限、发布、推送及版本查询的正式接口，后台可选人群／权限、推送渠道及测试环境；真实上网状态枚举仍须服务端核对。
2. 版本查询失败、已有有效强更策略、离线缓存与重试之间的衔接，不凭一次查询失败虚构新版本或放弃有效策略。
3. 无法安装新版设备的兼容与后续支持方式，避免反复要求无法完成的升级；目前未确定实际支持策略。
4. 正式版本发布是否自动生成更新消息、与人工发布和手机提醒如何关联的机制；不把人工系统公告默认关闭自动套成所有版本消息的最终机制。

正式业务UI仍需按已确认结构补齐，再由开发落实接口、平台能力与联调。沿用“开发自测联调 → 测试 → 产品体验验收”的顺序；隔离演示、原型源码检查不替代真实三端验证。
