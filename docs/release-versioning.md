# 知拍版本编号与交付规则

生效：2026-10-26。适用：原型交付、iOS／Android／鸿蒙 App、管理后台、后端接口服务和小程序。

**原型用「月.日-当天序号」；正式软件用三段式「主版本.次版本.修订号」。各交付物独立编号，通过同一份交付记录关联，不要求所有数字相同。**

本文件是团队执行依据。[原型交付台账](releases/prototype-deliveries.md)记录每次原型基线；[HANDOFF.md](../HANDOFF.md)管理三端还原范围。这里的 App、后台及小程序编号是团队统一规则，不表示当前仓库已有这些工程或已完成上线。

## 1. 一张表说明怎样编号

| 对象 | 采用的编号 | 示例 | 什么时候变化 |
| --- | --- | --- | --- |
| 原型 | 月.日-当天交付序号 | `10.26-1`、`10.26-2`、`10.27-1` | 每次向原型 `main`／团队交付分支正式推送新基线；仅文档更新也计入 |
| App 用户可见版本 | 三段式 | `1.4.6` | 发布新功能、修复或不兼容升级时按范围递增 |
| App 内部构建号 | 每端独立递增 | iOS build、Android／鸿蒙 versionCode | 同一用户可见版本再次打包交付测试、提审或发布时递增 |
| 管理后台 | 独立三段式 | `1.2.0`（仅举例） | 后台自身发布新代码时更新 |
| 后端接口服务 | 每个独立发布服务使用三段式 | `2.3.1`（仅举例） | 服务自身发布新代码时更新；同时记录兼容范围 |
| 小程序 | 三段式＋内部上传记录 | `1.4.6`，第2次上传（仅举例） | 正式发布按三段式递增；同版本重新上传用记录序号和 Git 提交区分 |
| 产品需求迭代 | 产品范围名称 | `V1.4.6` | 产品确认新的需求范围时变化；不是某个安装包的唯一标识 |

本表的编号用于解释格式，实际交付以台账和远端标签为准；首个原型交付登记为 `10.26-1`。App、后台及小程序示例不表示已经发布。`package.json` 当前工程版本不参与原型日期编号，也不作为 App 上架版本。

## 2. 原型推送强制规则

### 编号和使用边界

1. 按北京时间（Asia/Shanghai）的实际交付日期编号，当天从 `1` 开始。同一天第二次正式推送就是 `10.26-2`，第二天从 `10.27-1` 开始。
2. 日常修改、本地 Git 提交不单独占用原型版本；一次正式推送可以包含多个提交。用户要求「推送 git」至本原型 `main` 时，必须执行本节，不能因只有文档修改而省略。
3. 同一基线先推送、之后部署站点、再通知团队，属于同一次交付，沿用同一原型版本。出现新的源代码或文档提交后再次交付，分配新版本。
4. 一个版本只绑定一个确定的 Git 提交，不能覆盖、移动标签或把同一版本重新指向新内容。修正已交付内容时产生新版本；仅重试失败的同内容推送不重新编号。
5. 用户看到的编号始终保持简短。台账额外记录完整年份和日期；内部 Git 标签使用 `prototype/2026/10.26-1`，解决跨年重名，不能只用会移动的 `main` 或 `HEAD` 作为精确还原依据。
6. 已预留并创建标签的编号不回收。未成功交付的标签保留失败事实；内容改变后使用下一序号，不强制覆盖旧标签。

如果远端已经是本次目标提交，且没有新的交付内容，直接报告「已是最新，无需推送」，不为了凑一次版本创建空发布记录。

### 每次正式推送必须完成

| 顺序 | 必做事项 | 完成证据 |
| --- | --- | --- |
| 1 | 检查本次范围、已有台账、当地日期及本地／远端标签，取得当天未使用的下一序号 | 不复用已预留或已交付编号 |
| 2 | 同步相关产品／设计／交付文档，在台账新增本次记录 | 版本、完整日期、目标迭代、分支、标签、变更及验证／待验收项齐备 |
| 3 | 执行与修改范围匹配的检查，提交相关文件 | 提交说明含原型版本；不混入凭据、真实用户照片或无关改动 |
| 4 | 在确定的交付提交上创建同名不可变 Git 标签 | 标签解析得到唯一完整提交号；台账在同一提交内通过标签引用自身，不预填未来 SHA |
| 5 | 推送交付分支及该标签，核对远端两者实际结果 | 明确交付提交已在远端分支历史中，远端标签解析为同一完整提交号 |
| 6 | 提供可复制的企业微信群通知 | 原型版本、分支、实际短提交号、目标迭代、编号变更及验证／待验收状态 |

**缺少版本、台账、确定提交、标签或变更说明，不得作为正式原型推送完成。** 分支成功而标签失败属于交付未完成，必须如实报告；不能提前通知团队已经完成交付。推送失败时保留同一基线重试，若日期已经变化且尚未成功交付，则按实际日期重新编号，旧预留编号不再挪用。

代码推送、站点部署、用户验收、原生 App 提审和上架分别记录。推送成功不代表站点已更新，也不代表用户已经验收。仅本地提交无需原型交付版本，必须明确「尚未推送」。

从下一次获授权的正式推送开始执行；不追改历史提交，也不把今天的示例当作已经发布的版本。当前为工作约定和文档约束，尚未安装 Git hook 或 CI 自动拦截；执行者必须按清单核对。

### 企业微信群通知固定格式

```text
【知拍原型更新】代码已推送至 <分支>，提交号 <实际短SHA>。
原型版本：<月.日-序号>。
对应需求：<产品迭代，例如 V1.4.6>。
更新内容：
1. <具体变更一>
2. <具体变更二>
3. <实际验证结果及待验收项>
```

仅本地提交时首行改为「【知拍原型更新】已完成本地提交，分支 <分支>，提交号 <实际短SHA>，尚未推送。」；不填未产生的正式原型版本。站点有无部署单独如实说明。只提供通知文本，不自动发送到群。

## 3. App：统一三段式，构建号独立

用户可见版本统一为 `主版本.次版本.修订号`，不再新增四段式版本。

| 变更范围 | 编号规则 | 示例 |
| --- | --- | --- |
| 原版本功能范围内的修复、兼容及小调整 | 修订号加1 | `1.4.6 → 1.4.7` |
| 增加一批新的产品功能 | 次版本加1，修订号归0 | `1.4.7 → 1.5.0` |
| 产品级重大升级或明确不兼容变化 | 主版本加1，其余归0 | `1.5.0 → 2.0.0` |
| 同一正式版本继续测试／提审 | 用户可见版本保留，内部构建号递增 | `1.4.6` 的后续测试包使用新的 build／versionCode |

这是团队采用的递增语义，不是各应用商店统一强制的功能分类。App 内部构建号不拼成第四段用户可见版本。

| 平台 | 用户可见字段 | 内部构建字段 | 团队执行规则 |
| --- | --- | --- | --- |
| iOS | `CFBundleShortVersionString` | `CFBundleVersion` | 展示三段式；内部使用递增整数，沿用既有最大值继续增加 |
| Android | `versionName` | `versionCode` | 展示三段式；code 沿用既有最大值继续增加，不复用已上传值 |
| 鸿蒙 | `versionName` | `versionCode` | 展示三段式；核对项目级配置覆盖后的最终值，code 沿用既有最大值继续增加 |

三端内部编号各自管理，无须相同；iOS 连续递增整数是团队选择，不表述为 Apple 要求所有版本之间都不得重置。再次交付的包不得沿用旧内部编号，即便只是更换配置或修复一次提审问题。

同一批功能共同面向 `V1.4.6` 开发，但三端可以不同日期联调、验收、提审及上架。单端发布修复后可能出现 iOS `1.4.7`、Android `1.4.6` 的并存，交付表记录实际范围，不能为了数字一致伪报另一端已完成。历史鸿蒙四段式如 `1.4.5.1` 保留原记录；迁移到新的三段式时核对历史上架及构建值，不能直接截断为 `1.4.5` 或重置 versionCode。

三端还原进度通过工作日任务和阶段验收管理，同一正式版本可以交付多轮测试包，不为每一天另造一个 App 上架版本。真正新增已发布内容时再按上述规则递增。

平台字段依据：[Apple 展示版本](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleshortversionstring)、[Apple 构建版本](https://developer.apple.com/documentation/bundleresources/information-property-list/cfbundleversion)、[Android 版本配置](https://developer.android.com/studio/publish/versioning)、[鸿蒙构建配置](https://developer.huawei.com/consumer/cn/doc/doccenter-deveco-studio/ide-hmos-hvigor-build-profile-app)。实际提交前由平台工程师核对最终产物及对应商店记录。

## 4. 后台／后端：分别记录，不跟着 App 强行改号

「后台」分为供运营、机构使用的管理界面和向客户端提供接口的服务端；它们可能独立发布，不能混成同一个版本。

- 管理界面、每个独立发布的后端服务，均采用三段式并沿用自身现有历史；当前未提供工程和已发布版本，不能预填为 `1.4.6`。
- 修复增加修订号；兼容的新功能增加次版本；破坏兼容的变化增加主版本，并明确客户端迁移和旧接口保留安排。版本号本身不能替代兼容性说明。
- 服务部署记录包含服务名称、版本、Git 提交／制品标识、环境、部署时间及兼容的客户端版本。测试、预发布、生产是环境，不是第四段版本号；同一制品晋级环境不换成另一份内容。
- API 契约版本与后端程序版本分开。若今后采用 `/v1` 等契约标识，同一契约可以经历多个后端修复版本；此处不宣称现有真实接口已经存在。
- 后端先发布兼容接口、客户端分批接入时，在交付表写明可用接口、限制及最低客户端要求；不要求服务端与 App 数字同步。
- 回滚只使用可追溯的历史制品并记录操作，不覆盖历史版本内容。App 降级、数据库回退及接口兼容不能仅凭编号推断可行。

## 5. 小程序：三段式＋每次上传记录

- 正式展示／上传使用团队三段式编号，递增语义同 App，但沿用小程序自身版本历史。
- 同一个拟发布版本多次测试上传时，记录「第几次上传＋Git 提交＋上传时间＋平台返回标识」，不通过增加第四段来区分测试包。正式版本发布后再次发布修改，使用新版本。
- 开发、体验、审核和正式发布分别记录其状态，不把「已上传」写成「已上线」，审核驳回后重新上传必须留下新的上传记录。
- 当前未明确微信、支付宝或其他平台，也未提供小程序工程；各平台实际可填字段、格式限制和上传流程在接入时核对。不能假设所有小程序都有 App 的 versionCode。

## 6. 怎样把各版本关联起来

产品确认 `V1.4.6` 的需求范围后，研发选择一个确定原型版本作为还原基线。原型继续更新不等于该迭代自动追加需求；必须明确新增内容纳入本轮还是后续版本。仍在讨论或待验收的页面要单列，不能标为已冻结。

每轮联调／正式交付共用以下记录，填实际值而非强行统一编号：

| 对象 | 必填关联信息 |
| --- | --- |
| 产品范围 | 迭代、包含／不包含的功能、验收状态 |
| 原型 | 年份＋日期序号、不可变标签、解析后的完整 Git 提交 |
| iOS／Android／鸿蒙 | 各端用户可见版本、内部构建号、源码提交、测试／提审／上线状态 |
| 管理后台／后端服务 | 各自版本、源码提交／制品、环境、API 兼容范围及部署状态 |
| 小程序 | 所属平台、正式版本、上传记录、源码提交及审核／发布状态 |
| 共同验收 | 接口联调范围、已执行检查、待完成项、接收人与日期 |

本仓库当前提供 React 移动 Web 原型及交付资料；原生工程、真实后台服务和小程序尚未提供。建立规则本身不修改工程版本，也不自动授权提交、打标签、推送或部署；后续获用户授权的交付按本规则及台账执行。
