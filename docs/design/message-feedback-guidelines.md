# 知拍全项目消息反馈规范

日期：2026-10-26｜产品版本：1.4.6｜模式：Operate。

**状态：分类、位置及两张结构样图已获用户确认，统一组件及各模块整改待实施。** 本轮只更新规范和整改清单，未修改业务UI、路由、消息发送、付款或存储。当前项目仍是React移动Web原型，iOS、Android、鸿蒙是还原目标。

依据：[DESIGN.md](../../DESIGN.md)、[产品上下文](../../PRODUCT.md)、用户提供的“登录成功”遮挡首页头图截图，以及已确认的[轻反馈结构](../reviews/message-feedback-20261026/01-light-feedback.png)与[确认、失败和制作中结构](../reviews/message-feedback-20261026/02-decisions-and-processing.png)。图片是消息层级和位置的结构示意，不是实际页面截图，不代表重设计首页、身份表单或照片制作布局。

## 一、目标与边界

让用户准确知道发生了什么、是否需要处理、如何继续；消息强度随任务需要变化，轻反馈克制，错误就近，原因可读，关键操作先确认。

- 覆盖个人制作、六项工具、冲印、相册、账号、个人中心、客服／分享、专项采集、扫码和订单。
- 统一消息职责、出现位置、字排、反馈强度、生命周期和恢复规则，不把所有消息改成同一个Toast或弹窗。
- 业务通知中心的项目／采集消息、订单交易状态和照片审核状态继续由原业务承载；瞬时反馈不能替代通知记录、任务进度、交易凭据或完成页。
- 不因“统一”新增业务步骤、二次确认、退款／客服入口，或改变工具照片来源、照片保存目的地、项目认证及付款规则。
- 原型的“选择演示场景／选择制作结果”弹窗是演示控制，不是正式App的消息反馈范式。本轮不删除演示能力，也不把模拟选择当真实检测或制作。

## 二、六类反馈的使用规则

| 类型 | 用途与例子 | 位置／交互 | 结束条件 |
| --- | --- | --- | --- |
| Toast轻提示 | 复制成功、无需后续操作的短信息 | 当前活动页面或抽屉内，靠下居中，无遮罩、无按钮、不抢焦点 | 默认约2秒，两行约3秒；遵循平台无障碍推荐时长 |
| 页内提示 | 缺少学号、格式不正确、需要重选底色 | 就近放在字段或设置下方，错误与所属内容保持关联 | 修改后重新校验；修正或用户离开该任务后消失 |
| 模块提示条 | 相册读取失败、网络／服务异常影响当前步骤 | 放在受影响模块附近，必要时提供唯一重试动作；不会盖住照片和输入 | 重试成功或状态解除后结束，需处理的信息不自动消失 |
| 确认对话框 | 删除照片、丢弃未解锁成片 | 居中，简短说明对象与后果，沿用已有确认容器与具体操作按钮 | 用户明确取消或执行，提交中阻止重复操作 |
| 原因上滑抽屉 | 检测未通过、照片制作失败、服务不可用、审核／扫码详细原因 | 复用现有公共抽屉，原因直接可读，底部承载原业务恢复动作 | 用户关闭或按原流程继续，不定时关闭 |
| 制作中阻断层 | 已确认不能中断的个人证件照制作 | 同页阻断层，显示当前操作，无取消入口，锁定底页与返回 | 成功进入既定结果，失败先关闭Loading再展示原因抽屉 |

超过两行、需要解释原因或用户执行动作的信息不得塞入Toast。存在已确认的就近反馈（例如订单编号复制状态）时优先保留其职责，不为统一而再加一条Toast。

## 三、Toast视觉与位置

以下为本次已确认的目标值，**不是所有模块已经实现的样式**；现有生产组件差异见[整改清单](../reviews/message-feedback-20261026/remediation.md)。

- 深蓝灰表面，白色文字；圆角12px、字号14px、单行最小高度44px。图中深蓝灰`#26364A`作为已确认目标参考，实施时记录最终生效值；不新增外发光、全屏磨砂或大幅装饰。
- 宽度随文案自然变化，左右距离页面边缘至少24px；最多两行，文字不截断、不压缩字号。短文案不拉成接近整屏宽度的黑条。
- 水平居中，默认置于当前导航／固定操作栏上方16px，适配实际系统安全区和当前键盘；不是固定在屏幕某个百分比或某个首页坐标。
- 不覆盖系统栏、底部导航、当前主按钮。照片或表单问题使用就近提示／原因抽屉，不把重要原因压在照片或输入框上。受限空间无法避让时改用合适的就近反馈，不为Toast重排或压缩既有照片布局。
- 抽屉打开时反馈属于该活动层；不在被遮罩的底页上弹Toast，不穿透支付／确认层。确认框、阻断制作、失败抽屉出现时收起或抑制低优先级Toast。
- 无遮罩、无点击关闭要求、无操作按钮，不获取键盘焦点；必要小图标最多一个，使用现有线性图形和16px尺度。成功可使用勾，普通信息不用成功图标冒充成功。
- 同时最多一条，相同事件与文案去重；不堆叠、不排队播放过期消息。路由、任务、选中照片或账号改变后丢弃不再相关的消息和迟到结果。
- 使用现有克制淡入淡出，不弹跳、不缩放正文；减少动态效果时去掉位移。业务代码落地前不新增一套未经确认的动画体系。

## 四、页内提示与模块提示条

### 页内提示

字段标题、输入区与错误说明保持共同左边线。错误以明确文字说明问题，并给已知且可执行的修改方式；错误颜色与图标辅助识别，不依赖颜色单独传达。正文沿用任务14px层级，保留输入框原16px字号及44px触控规则。

空字段、格式问题不要用全局Toast代替。修改后按原验证时机重新校验，不因开始输入就把仍然存在的问题当作已解决。不得清空其他已填字段、原图或已选设置。

### 模块提示条

提示条在受影响模块的消息区域内自然排布，正文与内容保持现有16px等对齐线；通常使用一至两行说明，原因较长或包含多条明细时进入原原因抽屉。正常运行时不留下空提示卡。

- 信息、警告、失败分别使用现有浅底及语义文字；品牌蓝用于操作，不将所有消息做成高饱和蓝块或所有异常都做红色大卡。
- 提示条中的“重试”和底部主要操作不得同时执行同一请求。只保留一个明确恢复入口；其他按钮是否禁用由原业务依赖判断。
- 持续异常不自动消失。可以手动收起的非阻断信息按原场景设置关闭；收起不能伪造服务已恢复、项目可采集或允许付款。
- 短暂反馈不插入列表撑开固定布局。需要持续处理的模块状态按其模块显示，不把所有异常都固定悬浮在导航或首页头图上。
- 付款结果未知、保存失败、读取失败保留原业务的查款／重试保存／重试读取入口，不用泛化“重试”重复收费、制作或建单。

## 五、确认框、原因抽屉与Loading

### 确认对话框

沿用当前相册居中白色确认容器（16px圆角、18px标题），主次操作继续采用48px高度、14px圆角、15px字号。说明只包括操作对象和已知后果，危险动作使用原语义色，不把一般返回渲染成危险操作。

按钮使用“取消／删除”“继续查看／返回调整”等具体动作，不用“是／否”“确定／确认”掩盖结果。只有业务已经要求确认的删除、丢弃等动作采用对话框；选择规格、检查通过、常规保存成功不追加一次确认。

打开后锁定底页并移交焦点；Tab限制在当前层内。可取消的确认，系统返回／Escape按取消处理；执行中按原业务防重复，不用关闭覆盖层伪装成已撤销真实操作。关闭后返回触发控件和原滚动位置。

### 原因上滑抽屉

24px顶部圆角、18px标题、44px返回／关闭触控区、固定头尾与独立滚动正文；主按钮48px高、14px圆角、15px字号，底部按实际安全区避让。不得用整屏红色、巨型错误图或重复卡片加强提醒。

| 业务状态 | 必须保留的含义与动作 |
| --- | --- |
| 检测未通过 | 统一说明＋后台配置的检测项及结果；不由前端根据无人像／多人／动物等情景硬编码定向原因或指导 |
| 照片制作失败 | 直接展示实际失败原因；按原流程返回调整，保留原图和有效设置 |
| 制作服务不可用 | 说明服务异常及返回／稍后再试；不要求用户更换照片，不把服务故障归咎于照片 |
| 专项审核／上网异常 | 保留当前任务的业务状态、实际原因和已确认的恢复动作；不以全局Toast替代任务详情 |
| 扫码失败 | 区分读取、解析、机构／项目关联与身份核验，沿用来源相关的重选／重扫／查看项目；不能把非空码当作验证通过 |

### Loading与完成结果

阻断Loading仅用于已确认不能打断的个人证件照制作；其他工具的检查／处理继续沿用照片范围内动效、照片下方状态及当前步骤按钮锁定，不统一改成全页弹窗。扫码逐帧识别、相册读取和模块数据加载保留各自就近状态。

文案描述真实动作，如“正在制作照片…”。不编造百分比、剩余时间或“即将完成”。异常、超时、进入结果均必须清理旧Loading；网络／页面生命周期中断按原业务恢复，不永久锁屏。

制作成功、付款成功、结果归档／保存成功等已经由既定结果页表达时，不再同时叠加成功Toast、成功弹窗及完成页。Web已发起下载不等于写入手机相册，分享面板关闭不等于发送成功，支付返回不等于到账；既有演示文案与三端真实能力边界见[HANDOFF](../../HANDOFF.md)。

## 六、全局调度、文案与无障碍

- 一个事件选择一个主要反馈载体；顺序状态可以前后替换，不能让Loading、失败抽屉及旧成功Toast同时存在。
- 阻断操作／确认、原因抽屉、持续模块状态优先于Toast。优先级只管理反馈层，不取消实际业务请求或改写订单状态。
- 展示宿主属于当前活动页面／抽屉，不按整个App共用一个硬编码z-index随意盖层；账号、来源路由、当前任务和异步代次一起决定消息是否仍有效。
- 轻反馈采用不抢焦点的礼貌播报；需要处理的错误就近关联并按适当时机播报。逐帧扫描和每次进度刷新不重复打断读屏。
- 需要操作的错误或长原因不定时消失。字体放大后允许自然换行；读屏、减少动态、平台推荐停留时间和长文案按实际设备验收，不能只按Web固定402×874布局还原。
- 文案顺序为“发生了什么—确知的原因—下一步”；不知道原因时如实说明暂不可用，不编造服务端诊断、不输出内部异常堆栈或接口码。
- 保留知拍固定名词：照片规格、知拍相册、手机相册、支付成功、待签收等。通知用语不得把设备下载写成已入知拍相册，或把照片保存写成已完成审核。

## 七、未决项与实施边界

1. **“登录成功”提示是否取消仍待单独确认。** 用户已确认全项目范围、六类反馈和结构图；“减少重复成功提示／保留提示只统一样式”的单独选择未收到明确答案。本次不把样图确认解释为删除现有业务文案。
2. 本轮在`src/`中未检索到“登录成功／登陆成功”精确文案，不能据此断言截图来自哪个SDK或页面。实施时需依据实际App／原型包定位消息来源，避免Web与原生层重复显示；在项目源码中存在的其他Toast可独立整改，不被此项阻塞。
3. 本规范是已确认目标；当前仍有居中Toast、顶部通知和页内消息的旧实现。不得把已写规范、静态源码核查或已确认结构图写成统一组件已完成或实际视觉已验收。
4. [.impeccable/design.json](../../.impeccable/design.json)暂不新增六类虚构“已实现组件”。后续实际组件完成并验收后，再同步提取真实示例与最终值。

## 八、验收方式

实施顺序与各模块前后流程见[逐模块整改清单](../reviews/message-feedback-20261026/remediation.md)。每项完成交用户验收后再推进下一项；没有新授权时不自动修改业务页面或发布。

验收重点：相同事件不重复、无头图遮挡、主操作与系统区可达、照片失败原因可读、字段错误能就近修正、返回／键盘／抽屉层级一致、异步结果不跨任务残留、付款和保存不被重复触发。

本轮只核对源码与文档，不自动操作浏览器、截图或运行自动UI测试；结构图不代替手机实际画面与三端真机验收。
